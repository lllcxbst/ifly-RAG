# 部门产品智能客服机器人研发—AI 提效实践报告

## 一、课题说明

“航标”面向平台/API 产品使用者和一线技术支持，将重复的功能咨询、接入指导和常见错误排障自动化。目标不是让大模型自由回答，而是构建一条“问题—证据—答案—引用—反馈—评测”的闭环。

目标用户包括业务研发、解决方案、交付人员和技术支持。应用场景覆盖产品能力了解、API 参数/接入步骤查询、错误码和异常结果排查。系统边界是：只回答知识库内信息；账号、计费、生产事故和依据不足问题转人工；不操作用户环境，不暴露密钥。

## 二、产品调研与知识库

本次收到的附件仅为作业说明，没有提供真实部门产品清单、导师访谈或正式 API 文档。为保证可运行交付，系统内置“星河 API 开放平台”虚构样例，覆盖产品定位、核心功能、场景、接入方式、使用步骤、鉴权、异步任务、回调、限流、常见错误和转人工条件。所有页面和源文件均标记为演示资料，防止与真实产品混淆。

真实调研资料可在管理台按“官方文档、FAQ、导师访谈、故障复盘”标注来源并增量导入。正式验收前应完成真实部门产品替换，并由导师或产品负责人确认 30 题答案。

## 三、技术方案

系统采用统一 Web 问答后端和 Web 页面交付形态。前端为 React + TypeScript；后端为 FastAPI；PostgreSQL + pgvector 保存结构化数据和向量；Redis 提供限流；模型层适配任意 OpenAI 兼容的 Chat/Embedding 服务。

选择“大模型 + RAG”而非微调：资料变化时只需重新索引，不必训练；来源可以追溯；未知问题能基于检索分数硬拒答。优势是更新快、可解释、成本可控；不足是检索召回决定答案上限，模型调用有时延，复杂表格和扫描文档需要预处理。系统用结构化切分、混合排序、Top-K 融合、引用校验、拒答阈值和回归评测补偿。

完整链路：文档解析 → 按标题/句子切分 → 批量 embedding → pgvector 索引 → 问题分类 → 向量候选 + 关键词融合 → 置信度门控 → 受限生成 → 引用校验 → 记录和反馈。

## 四、核心能力体验

### 能力一：可追溯接入问答

输入：“接入平台前需要准备什么？”

预期体验：机器人说明控制台创建应用后获得 `app_id`、`api_key`、`api_secret`，强调 secret 只能存服务端密钥系统，并给出对应“接入前准备”原文卡片。用户点击回答中的引用编号，右侧证据台同步定位原文和匹配度。

### 能力二：顺序化智能排障

输入：“调用返回 AUTH_001 怎么解决？”

预期体验：机器人按环境凭据、服务器时间、签名路径、请求体字节摘要和编码顺序排查，引用错误码章节；若仍失败，引导提交包含时间、request_id 和脱敏请求头的工单，并明确禁止提交 secret。

### 边界体验：拒绝编造

输入：“明天北京天气如何？”

预期体验：检索分数低于阈值，不生成天气答案，明确当前知识库没有可靠依据并引导人工或改问产品问题。

## 五、评测与一轮优化

评测集共 30 题：功能介绍、使用方法、问题排障各 10 题，其中包含一个知识边界外问题。断言使用关键事实命中与正确转人工，数据在 `data/evaluation/questions.json`。

第一轮离线回归结果：

| 方案 | 整体 | 功能介绍 | 使用方法 | 问题排障 |
|---|---:|---:|---:|---:|
| 优化前：字符/词重叠 Top-1 | 66.67% | 90% | 60% | 50% |
| 优化后：bigram + 查询扩展 + 标题权重 + Top-5 | 96.67% | 100% | 90% | 100% |

优化前典型失败是用户用“报错怎么办”而文档标题写“常见错误”，以及答案事实位于第二或第三候选片段。优化后加入中文 bigram、同义查询扩展、标题加权和多证据融合。剩余失败 U05（`top_k` 配置）说明宽检索可能把相邻接入资料排在参数章节前；下一轮可加入 cross-encoder reranker 或按接口名做实体加权。

结果由 `python3 scripts/evaluate_retrieval.py` 生成并写入 `docs/evaluation-results.json`。随后在完整 Docker 栈中运行管理台端到端评测：初次混合检索通过 23/30（76.67%）；分析“永久保存、轮询、时钟慢、429、回调重试”等失败表达后，加入 pg_trgm 词面候选与向量候选合并、领域查询扩展、精确错误码加权和动态证据下限，最终通过 30/30（100%，三类各 100%）。摘要见 `docs/evaluation-e2e-summary.json`。

100% 是虚构演示知识和固定回归集上的工程验收结果，不代表真实产品上线精度。导入真实部门资料并配置生产模型后，必须由产品负责人确认标准答案、增加真实失败样本并重新评测。

## 六、异常、日志与安全

服务记录问题、回答、类别、置信度、引用、模型和耗时；每个 HTTP 响应带请求 ID。Redis 故障时仅降级限流，不使问答下线。模型或 embedding 不可用返回统一 503，不向用户泄露内部堆栈。

密钥来自环境变量；上传限制类型和大小；管理接口使用独立密钥；IP 加盐哈希；文档被当作不可信上下文，文档里的越权指令不会作为系统命令执行。生产环境应追加 SSO/IP 白名单、TLS、集中日志和定期备份。

## 七、AI 提效过程与总结

AI 用于需求拆分、技术对比、数据模型、代码骨架、样例知识、测试集和界面实现。人工/工程判断主要集中在：把演示资料与真实产品严格隔离；拒答优先于覆盖率；选择适合部门级规模的中间件；让“证据”成为界面核心；对 AI 生成代码做构建、语法、评测和安全校验。关键记录见 `docs/AI研发记录.md`。

项目经验是：客服机器人的价值不是“像人一样能聊”，而是稳定减少重复支持工作。可靠来源、明确边界、失败可升级、问题可回放、效果可量化，缺一不可。

## 八、交付与演示建议
